# Why it misses
Fast cryptographic hashes like SHA-256 or MD5 were designed to verify file downloads quickly (calculating billions of hashes per second). An attacker with a modern GPU can crack an 8-character SHA-256 password hash in seconds using Rainbow Tables or brute force.

<Steps>
  <Step icon="lock" title="1. One-Way Hashing vs Two-Way Encryption">
    - **Encryption**: Two-way. Given a ciphertext and a private key, the original password can be decrypted back to plain text.
    - **Hashing**: One-way. Mathematically impossible to reverse a hash back to its original plain-text password.
  </Step>
  <Step icon="key" title="2. The Role of Cryptographic Salt">
    A **Salt** is a unique, cryptographically random string generated per user and appended to the password before hashing (`hash(password + salt)`). This guarantees that two users with the same password (`password123`) produce completely different hashes, destroying precomputed **Rainbow Table** dictionaries.
  </Step>
  <Step icon="shield" title="3. Adaptive Work Factor (bcrypt & Argon2)">
    Algorithms like **bcrypt** and **Argon2id** are intentionally designed to be CPU/memory intensive with an adjustable **Work Factor (Cost Factor)**. Increasing the cost ensures verification takes ~100ms on a server—negligible for a real user, but cripplingly slow for brute-force attack clusters.
  </Step>
</Steps>

<Tip title="Modern Standard">
Use **Argon2id** (winner of the Password Hashing Competition) or **bcrypt** (cost factor 12+) using well-maintained libraries. Never invent custom hashing logic or use raw MD5/SHA-1/SHA-256 for passwords.
</Tip>
