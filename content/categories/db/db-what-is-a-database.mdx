# Why it misses
Saving data into a simple `data.json` file works fine for a single person, but fails catastrophically in production when multiple users attempt to read and write at the exact same time (race conditions, file corruption, locking).

<Steps>
  <Step icon="clock" title="1. Concurrency & Race Conditions">
    If User A and User B both update `data.json` at the exact same millisecond, writing the whole file overwrites and corrupts one user's changes. Databases use row/table-level locking to handle millions of simultaneous reads and writes safely.
  </Step>
  <Step icon="search" title="2. Indexing vs Full File Scans">
    Finding one user in a 10GB JSON file requires reading the entire 10GB into RAM every query ($O(N)$). Databases use B-Tree indexes to find a row in microseconds ($O(\log N)$).
  </Step>
  <Step icon="shield" title="3. ACID Safety & Crash Recovery">
    If the server loses power in the middle of writing a JSON file, the file is corrupted. Databases use Write-Ahead Logging (WAL) to guarantee transactions either finish completely or roll back safely.
  </Step>
</Steps>

<Tip title="Mental Model">
Think of a JSON file like a notebook in a library. Only one person can write on the page at a time without fighting for the pen. A database is an automated computerized filing vault that coordinates thousands of readers and writers simultaneously.
</Tip>
